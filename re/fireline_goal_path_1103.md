## 1. What 0x8f6990 is
- Signature: `__thiscall`, `ret 8`. `this` (ecx, kept in edi) = object B (the same B as `[ZSoldier+0x698]`; `[B+0x154]` = the owning ZSoldier, `[[B+0x154]+0x40]` = its actor). Return: `al` (bool = the result of 0x5706a0; the epilogue 0x8f6a27-0x8f6a2c does not touch eax).
- Args (stack): `[ebp+8]` = `float *v` (a vec3, read at 0x8f6996-0x8f69aa and copied to locals `[ebp-0x18..-0x10]`), `[ebp+0xc]` = `DWORD *out` (passed unchanged to 0x5706a0 as its third arg, which fills it from 0x51bf80 at 0x5707dd; the caller reads it back).
- Body (0x8f6990-0x8f6a2c, no loop, no yield): builds the other end of the segment in a local vec3 `[ebp-0xc..-4]`: `0x7836b0(actor, -1)` (a lookup on `[[B+0x154]+0x40]`, what it finds: GUESS, a bone / attachment); if found and its vcall `+0x30` masked with `[0x1535218]` equals `[0x1535214]` -> `0x71c5d0(esi, &vec)` (fills the vec3), else zero vec3 + `0x7b3020([[actor]+4], &vec)` and z += qword `[0xb4be50]`. Then `push out; push &local(ebp-0x18); push &vec(ebp-0xc); ecx=edi; call 0x5706a0` (0x8f6a1c-0x8f6a22). A thin wrapper: "is a friend in the line from the soldier to v?".
- Prologue bytes: `55 8b ec 83 ec 18 8b 45 08`; the first three instructions are exactly 6 bytes (push ebp / mov ebp,esp / sub esp,0x18), position independent.

## 4. TEST-only design (SUPERSEDED by the verification: on the goal path 0x655a40 is a constant-false stub, so this detour would change nothing; kept for the record only)
No private-table option exists, so a code detour is the only way. It must be a labelled TEST toggle (ship builds never patch code).

Proposal: new ini key `[Brain] OnlineBrainTraitorFireLineGoal` (default 0, "TEST ONLY, patches kl2.exe code"). Do NOT make it mode 3 of OnlineBrainTraitorFireLine: that key is the ship-safe private-table feature, and a mode that writes code should not hide behind it. Requires OnlineBrainTraitorFireLine >= 1 (klbr_tflmode, so the logic gate is shared) and OnlineBrainTraitorArcade=1; otherwise off with a log line.

Mechanism:
1. Detour 0x8f6990: read the 9 bytes first and expect `55 8b ec 83 ec 18 8b 45 08`, else refuse and log. Allocate a trampoline: the 6 stolen bytes + `jmp 0x8f6996`. Write `jmp rel32` + 1 nop over 0x8f6990..0x8f6995 through klh_poke (the patch guard, klhook.c:430, takes expect and new bytes). Undo: write the 6 original bytes back at round end / feature off.
2. Wrapper `static DWORD __fastcall klbr_w_flgoal(DWORD B, DWORD edx, DWORD a1, DWORD a2)` (thiscall, 2 stack args, ret 8, result in al): `soldier = [B+0x154]` (guarded read, > 0xffff); `m = klbr_tfl_begin(soldier, &sw, &e)`; org = the trampoline typed like klbr_fl114fn; `!m` -> return org(...); log only -> org then klbr_tfl_log; swapped -> org inside `__try/__except` like klbr_w_fl114, then `klbr_tfl_end(soldier, sw, flt, SLOT_GOAL)` (new id for logs, e.g. 115; klbr_ta[].nlog needs a third entry); on a fault return 0 (no friend in line is the permissive answer; GUESS that a fault is rare).
3. Reuse: klbr_tfl_begin / klbr_tfl_end / klbr_tfl_log / kbr_tfl_decide unchanged. klbr_tfl_begin returns 0 when `klbr_depth > 0`, so slot 113 -> 0x5bdfe0 -> 0x8f6990 (swap already in) just calls through and is never swapped twice. The swap is held only for the 0x8f6990 body (0x7836b0, the +0x30 vcall, 0x71c5d0, 0x7b3020, 0x5706a0). The direct callees of 0x5706a0 contain no yield (0x455b40 0x506090 0x508ef0 0x51bf80 0x5891f0 0x5a9720 0x660b00 0x6a1c40 0x6b8200 0x6cbf80 0x72a000 0x763e40 0x78f470 0x7b3020 0x7bb2a0 0x7f6850 0x7fd930 0x863a60 0x873dd0 0x87c980 0x8df480 0x929fc0). That is why this swap is safe where wrapping the goal methods is not.
4. Verify in the usual order: log only (human in the line, expect 1 online) -> swap on (expect 0 for the marked bot) -> OnlineBrainTraitorHitLog shows marked hits on humans > 0. Log the first 8 results per bot.

### A. What `[F+4]` is, and the three tests in 0x8c1830
- F (`[ZSoldier+0x6a0]`, ctor 0x557ae0 called from the ZSoldier init 0x615c90 at 0x615d7c, `[F]` = ZSoldier) gets `[F+4]` in its reset method 0x4f2460: `edi = 0x7836b0(actor = [[F]+0x40], -1)` (same lookup 0x8f6990 uses), stored at 0x4f252b. So `[F+4]` = the soldier's ACTIVE ITEM: any object whose class mask is the ZItem base (`[0x1535214]` is registered as class "ZItem" at 0xae1398/0xb64ca4, so it is not only a weapon; a non-ZItem object must pass `+0x2ec()->+0x2ac()`), in practice a ZFFItemWeapon (vtable 0xbc042c; ZItemWeapon 0xba3e6c has the same slots +0x2ec/+0x2fc). - Its slots (vtable dwords read): `+0x2ec` = 0x6ed320 = "get template" (returns `[item+0xc4]`; the body is not a one-liner: a type check on `[[item+0xc4]+4]+0x70` bit 10 with an `int3` + debug-print branch when the bit is clear, then it returns the same pointer; a ZItemTemplateWeapon / ZFFItemTemplateWeapon, vtables 0xba4ce4 / 0xbbf61c, identical slots here); `+0x2fc` = 0x511f50 = `[item+0xdc] ^ 0xbeebbeeb` (the obfuscated AMMO count). ### D. The real friendly-fire filter: 0x6e3400 (victim health change), after slot 15
0x6e3400 is `thiscall` on the VICTIM (esi = ZFFPlayer body), args `float delta` BY VALUE (the stack slot is modified in place; slot 15 gets its address) and `attacker` (ebx) (Verification 2: corrected from "float *delta"). The filter, in order (read from code):
1. `edi = attacker` only if its class mask matches `[0x1548c7c]` (0x6e344b-0x6e3462), else edi = 0.
2. 0x6e3476: `[session+0x5c] != 4` -> skip every filter (damage lands). Online FA is mode 4 (earlier notes), so it continues.
3. Sub-mode `[0x168e59c]`: 2 -> branch 0x6e3490, 1 -> branch 0x6e34d2, 0 (FA: CONFIRMED, 0x502bee stores the Arcade FA value 0, re/cops_and_robbers.md "0 = FA, 1 = UCC, 2 = C&R", 0x5cacd9 tests ==0 as FA) -> 0x6e3542.
4. Sub-mode 0: `edi == 0` (attacker not a ZFFPlayer) -> jump 0x6e35fc = NO filter, full damage. `edi == victim` -> 0x6e35ab. Otherwise: attacker police (`+0x2723`) and victim police -> delta = 0; attacker police -> 0x6e35ab. Attacker not police: attacker traitor (`+0x2726`) OR victim police OR victim traitor -> 0x6e35ab (no zeroing). Else (two plain heisters, nobody a traitor): `0x7bb2a0(0x168e9e4)` returns the rules object (`[session+0x54]`, 0 if mode != 4) and its vcall `+0x2f4` = slot 189 = 0x4ee010 = `byte [rules+0x285]`; false -> `delta = 0` (0x6e35a5-0x6e35a7). Rules slot 190 (`+0x2f8`) = 0x8f3930 is the setter (`[ecx+0x285] = al`); constructors zero the byte (0x51be38, 0x70869c). CORRECTED (Verification 2; the first version said the setter was not found): the byte is "the looting has started". 0x5cac90 (callers 0x6bbd78, 0x7ceb4f, 0x881996, the loot paths) sets `[rules+0x285] = 1` at 0x5cacd2 once, FA slot 4 / Heist slot 4 / slot 7 (0x74bd92) clear it at round reset (re/fed_kit.md section 1; 0x5cac90 re-read: `cmp [esi+0x285],0; jne out`, ... `mov byte [esi+0x285],1`). So the step-4 zeroing is limited to the time BEFORE the first loot event of a round; afterwards two plain heisters take the 0x6e35ab path (x0.5 once, then a 10 s window, see 5).
5. 0x6e35ab onward: attacker and victim with the same police flag, neither traitor, and the victim's timer `[esi+0x2784]` not > 0 -> arms the timer and multiplies the delta by `[0xce8a40]` (a friendly-fire scale, GUESS; the file image holds 0.5, and the timer constant `[0xce8a3c]` 10.0; runtime writers not searched). The timer test is `0 < [esi+0x2784]` -> skip, so the 0.5 applies to the first hit and the timer then lets later hits through unscaled for 10 s. A traitor byte on either body -> 0x6e35fc: unmodified.
- Consequence (derived from the code; whether it bites live is UNVERIFIED): a marked bot of OnlineBrainTraitorArcade carries its mark only in the PRIVATE shadow record (`rec+0x79` bit 1) and the swapped role/table. 0x6e3400 reads the BODY bytes `+0x2726` / `+0x2723`, which the brain does not write for a bot (grep klbrain.c: no `0x2726`; only kladren.c / klfedkit.c write it, for the local human). The marked bot may therefore aim and shoot a human (nothing in 0x8c1830 stops it, section A) and still do 0 damage. OnlineBrainTraitorHitLog cannot see this: it counts ATTEMPTED hits in slot 15, BEFORE this filter (klbrain.c 987, 1002).
- The bullet routine 0x458880 (team code 0x458b00-0x458c48, reads the same `+0x2726` / `+0x2723` / `+0x2729` and `0x7bb2a0 -> +0x2e8`) only picks a hit-effect id (`[0xbbe498]` vs `[0xbbe49c]`, pushed to 0x8fdb20): cosmetic (GUESS, the tail after 0x458cb8 not read).
