# Traitor cap: who writes [rules+0x338], tuning [R+0x6c], what limits Arcade to ~1 traitor (static kl2.exe, read only)

Method: capstone linear sweep of kl2.exe .text (skipdata), helper `scratchpad/kdis.py`. R = [0x168d7c0] + 0x6ac + L*0x70, L = clamp([[rules+0x5f8]+0x45], 1, 11).
Unverified claims are marked GUESS. Nothing was run.

## 1. Writers of [rules+0x338] (rules = the object in [G+0x54])
Scan of every `0x338` operand in .text (168 hits; most are esp/ebp locals or other classes). The ones on the rules class:
| addr | function | what |
|---|---|---|
| 0x835771 `mov [esi+0x338], ebx` (ebx=0), 0x835777 `mov byte [esi+0x33c], bl` | ctor 0x835480 (sets vtable 0xbd3514, writes [esi+0x5f8], +0xda4, +0xe84) | zero at construction |
| 0x8c7abe `mov [esi+0x338], ebx` (0), 0x8c7ac4 `[esi+0x33c]=0` | round reset 0x8c7a80 (reads [esi+0x5f8], clears the 12 flag dwords at [score+0x1d4..]; callers 0x569544, 0x74bcf5, jmp stub 0x7f8e70) | zero at every round start |
| 0x432310 `inc dword [eax+0x338]` | 0x4322f0 (thiscall rules, char slot; called ONLY from Traitor RUN 0x488eb0 at 0x488ed8) | the only increment in .text, but DEAD CODE |
Dead-code proof (CERTAIN from the bytes): `edi = 1<<slot; edi |= movsx(byte [eax+0x33c]); jne skip` - the OR with a set bit is never 0, so the inc at 0x432310 never runs. Then `[eax+0x33c] = (1<<slot) & oldmask` (an AND, narrows). So in Arcade [rules+0x338] stays 0 all round (ctor/reset write 0). That confirms the repo's note "0x4322f0 never increments it".
Other `mov [reg+0x338]` sites (0x7fe62f, 0x8445e4, 0x8a0f9d, 0x8b7616, 0x65446e, 0x6c8490, 0x71717f, 0x79ace5, 0x7d7709): their functions do not touch +0x5f8 / the rules vtable; GUESS: other classes (same as arcade_brain_shadow_1102.md section 3). Readers of +0x338 on the rules: only 0x43ffb0 at 0x43ffca.

## 2. Tuning [R+0x6c] ("traitors allowed", 0x43ffb0 compares at 0x43ffdd `cmp ecx,[edx+esi+0x718]`)
Defaults from the tuning ctor 0x524050 (the `mov [eax+8], v` after `lea [edi+0x6ac+L*0x70+0x6c]`, ebx tracked sequentially):
L1-3 = 0, L4-5 = 1, **L6-8 = 2**, L9-10 = 3, L11 = 4.
(Level 6: 52e1b5 `lea edx,[edi+0x9b8]`, ebx=2.) GUESS: nothing overwrites the table later (not established; balance.md says the same for the whole table; klbalance.c logs the live values).
So at L6 the cap would be 2, not 1; at L1-3 the cap is 0 (no traitors at all, since 0 < 0 is false).
Roll in 0x43ffb0: band p = L<=2 0.05 / L<=5 0.10 / L<=7 **0.30** / else 0.40 (0xb39e08, 0xb4c788, 0xb26690, 0xb6fe50); LCG [[0xdd2640]+0xb30] advances on EVERY call (before the `ok` test), r = ((x>>8)&0x7fff)/32768, true iff ok && r < p.

## 3. The real gates in Evaluate 0x79b7c0 (and why Arcade turns ~1)
Order: (a) 0x7f6850() true; (b) timer: `[tactic+0x18] > [[0xdd2640]+0x48]` -> 0.0. The ctor 0x51b7e0 zeroes +0x18 and RUN 0x488eb0 never writes it; GUESS: nothing else writes it, so this gate never closes. (c) rules = 0x508ef0, slot = 0x78f470(...) stored to [tactic+0x14]; (d) G5 0x43ffb0 (cap [rules+0x338] < R+0x6c, then 0.30 roll at L6); (e) the SCORE test:
score = stageTerm[rec+0x78] + ownMoneyTerm + otherMoneyTerm, returns 1.0 iff score > limit (fcompp at 0x79b956, `test ah,5; jp`), limit = 0x46d4d0 = R+0x20.
Defaults (identical for L1-9; L10-11 only change the money thresholds to 100k/250k/750k):
- limit R+0x20 = **7.0**
- stage term by rec+0x78 (jump table 0x79b970): 0 -> R+0x24 = 0, 1 -> R+0x28 = 0, 2 -> R+0x2c = 2, 3 -> R+0x30 = 3
- own money m = vt[0xe0](slot of this bot) vs thresholds R+0x34/0x38/0x3c = 750k/1M/1.25M -> term R+0x40/44/48/4c = 0/1/2/3
- other money (row 0 = "the player", 0x6c7700 returns 0 in the Arcade frame) vs R+0x50/54/58 = 750k/1M/1.25M -> term R+0x5c/60/64/68 = 3/2/1/0
Max sum 9, need > 7, i.e. >= 8: only (stage 3, own >= 1.25M, other < 1.25M) or (3, own >= 1M, other < 750k) or (stage 2 with own >= 1.25M and other < 750k). That score test, not the +0x338 cap, is what limits Arcade: a bot must be at heist stage 2-3 with a big haul while the player is poor. The cap (value 2 at L6) is inert in Arcade because +0x338 stays 0 (sections 1-2). There is no other timer/per-round flag: RUN only sets rec+0x79 |= 2 and calls the dead 0x4322f0; Evaluate has no "already a traitor" test (GUESS: the bot leaves the list of candidates because its team flips elsewhere).
Consequence for bs7 (5 of 7 marked a round): the online inputs make the score > 7 for most bots: the stage byte (kbr_stage_byte, with BoardStage=1 gives 3 to a bot that carries loot while the van waits) and the money rows (own = [score+0x150+4*rec], row 0 = host or richest human) - GUESS that this, plus 30% per evaluation repeated all round, gives 5 of 7. Verify with the existing klog at klbrain.c:355-359 (prints sum, stage, bot, pl).

## 4. Recommendation
1. Arcade's own count rule does not exist in practice ([rules+0x338] never counts), so there is nothing to mirror by "increment on turn". Do NOT expect [shadow+0x338] to reproduce Arcade; Arcade's ~1 comes from the score gate.
2. If a cap is wanted, make it Arcade's tuning instead of the ini key: each pump (depth 0, already done at klbrain.c:885) write `[shadow+0x338] = number turned THIS ROUND (never decremented on death/boarding; zero it only at round start like 0x8c7a80)` and read the limit live: `cap = *(int*)([0x168d7c0] + 0x6ac + L*0x70 + 0x6c)` (2 at L6). Then 0x43ffb0 itself enforces it with the game's tuning (L1-3 would give 0 traitors, L9-10 three). Today klbr_trcap uses an ini number and kbr_tr_cap_word(klbr_tt_turned, cap) - GUESS that this writes turned count or 0; use "ever turned" rather than "currently turned" or a dead/boarded traitor frees a slot.
3. To get closer to Arcade's ~1, fix the INPUTS, which is where the difference is: (a) make the shadow stage byte (rec+0x78) 2/3 only where Arcade's heist stage would be (see what Arcade stage 2/3 means: reached exit/van? not "carries loot while the van waits"; BoardStage's extra stage 3 inflates the traitor score - GUESS), (b) keep row 0 = a real player's carried money (richest human makes the other-term small more often than host; try host), (c) keep the money thresholds in mind: bots rarely hold >= 1M each in Arcade. The ini TraitorMax (1) stays as the safety net; with Max=0 and live tuning, expect up to 2 at L6.

## Refute (adversarial re-check, static kl2.exe, re-disassembled with kdis.py; nothing run)

Method: re-scanned every instruction with displacement 0x338 (168 hits, same count), then classified each by function and by vtable stamp, not only `mov`. Checked lea/add (address-taken) forms, indexed forms (`[reg+idx*4+0x338]`), byte/word overlaps (0x339..0x33b), and all calls into the rules class.

### Verdicts
1. Writers of [rules+0x338]: CONFIRMED, with one correction to the reasoning.
   - 0x835771 (ctor 0x835480, stamps 0xbd3514 at 0x8354ba): zero. CONFIRMED.
   - 0x8c7abe (round reset 0x8c7a80; callers 0x569544, 0x74bcf5, jmp 0x7f8e70): zero, also byte +0x33c. CONFIRMED.
   - 0x432310 `inc dword [eax+0x338]` in 0x4322f0, only caller Traitor RUN 0x488eb0 at 0x488ed8: CONFIRMED. Dead code: `edi=1<<cl; edi|=movsx(dl); jne 0x432316` skips the inc, and (1<<cl) is never 0 (x86 masks cl to 0..31). The byte store `[eax+0x33c] = (1<<slot) & old` only narrows, so it stays 0. +0x338 and +0x33c are 0 all round.
   - No other writer of the Heist class found. All 168 hits searched: no add/sub/or/and/xchg forms, only the `inc` at 0x432310. The lea/add-ecx forms (0x4f0e0a, 0x4f122a, 0x527af9, 0x56b8a0, 0x5c4131, 0x5dd0eb, 0x604d27, 0x66b47f, 0x8556d4, 0x8bae17/47, 0x8dcd36, 0xad5bfc, 0xad6d4c, 0xadd90b, 0xaddb7b) are ctor/dtor calls on sub-objects of other classes or pass &member to a callee; none is in a function using [this+0x5f8] with the Heist vtable. The 4 `[esp+eax*4+0x338]` hits and ~95 esp/ebp hits are stack locals.
   - CORRECTION to the research text: 0x65446e `mov [esi+0x338],3` IS in a function that touches +0x5f8 (0x653e00 writes `[esi+0x5f8]` at 0x654a35). It is a different class (vtable 0xbd1f50 at 0x653e15, a ctor building sub-objects, 3 is a sub-object field), not Heist. The conclusion stands; the stated reason ("does not touch +0x5f8") is wrong for this site.
   - Other stores seen: 0x7fe605/0x7fe62f (class with count at +0x334 and array at +0x338), 0x8445e4 and 0x7d7709 (ctor-style zero runs 0x324..0x340), 0x71717f, 0x79ace5 (sibling class stamped 0xbd2eb4 sharing base ctor 0x7de590 with Heist; +0x338 = 0, +0x33c = 0x10), 0x8a0f9d, 0x8b7616 (vtable 0xbc703c), 0x6c8490 (lazy `new` of 4 bytes). All ctor/init writes of other classes. Heist has no derived class: the only caller of 0x835480 is the factory 0x725da0. UNVERIFIABLE as proof for 0x7fe62f, 0x8445e4, 0x7d7709 (callers not traced to the end), but no evidence they are Heist.

2. Tuning R+0x6c via the compare at 0x43ffdd (`[edx+esi+0x718]` = 0x6ac+0x6c, L*0x70): CONFIRMED. Re-read ctor 0x524050 with ebx tracked: L0 = 0xd (unused, clamp is 1..11), L1-3 = 0, L4-5 = 1, L6-8 = 2, L9-10 = 3, L11 = 4. At L1-3 `0 < 0` is false, so no traitor at all.
   - "Nothing overwrites it": my own scan cannot prove it (GUESS), but re/balance.md section 10.2 supports it (no fixed-displacement access into the eleven rows; the 786 descriptors are freed at the end of the ctor). Likely true.
3. Roll in 0x43ffb0: CONFIRMED. p = 0.05 (L<=2), 0.10 (L<=5), 0.30 (L<=7), 0.40 (else); the LCG at [[0xdd2640]+0xb30] advances on every call (store at 0x44002c is before `test cl,cl`); true iff cap-ok and r < p. 4. Evaluate order in 0x79b7c0 (7f6850, timer, rules 0x508ef0, slot 0x78f470 -> [tactic+0x14], 0x43ffb0, score): CONFIRMED. Stage byte is `[0x7fd930(slot)+0x78]` (rec = [rules+0x348] + slot*0x7c); jump table 0x79b970 = {0x79b8d4 (+0x24), 0x79b8c5 (+0x28), 0x79b8ca (+0x2c), 0x79b8cf (+0x30)}, default (>3) = +0x24. Money thresholds 750000/1000000/1250000 for L1-9 and 100000/250000/750000 for L10-11. Row 0 via 0x660b00 + 0x6c7700, which returns 0 when 0x7f6850 is true (Arcade). All CONFIRMED.
5. **WRONG: "returns 1 only if sum > 7.0". The correct test is sum >= 7.0.** At 0x79b94e `call 0x46d4d0` leaves the limit in ST0; 0x79b953 `fld [ebp-0x14]` pushes the score, so ST0 = score, ST1 = limit. `fcompp` sets C0 only when score < limit; C3 (equal) is not in the `test ah,5` mask, so equal gives result 0, PF set, `jp` taken, `fld1` at 0x79b967 (return 1.0). Fall-through 0x79b95f is `fldz`. So 7.0 qualifies (NaN also returns 1). With the default integer terms the sum reaches 7 for: stage 3 with own >= 1.25M and other < 1.25M; stage 3, own >= 1M, other < 1M; stage 3, own >= 750k, other < 750k; stage 2, own >= 1.25M, other < 1M; stage 2, own >= 1M, other < 750k. Stage 0 or 1 can never reach 7 (max 6). So "stage 2-3 needed" holds, "needs >= 8" does not.

### Final recommendation (revised)
- Do not build a "mirror Arcade's count" word: none exists (+0x338 is 0 all Arcade round and the cap never bites there). Any cap is hook policy, not parity. Do not read R+0x6c live: that would impose a cap of 2 that Arcade does not have.
- Keep the existing mechanism: `OnlineBrainTraitorMax=N` writes 0 / 0x7fff from the ever-turned count and 0x43ffb0 enforces N itself. Max=1 is a reasonable default for an Arcade-like feel; Max=0 equals Arcade's actual (uncapped) behaviour. Fix the comment at klbrain.c:885: the word is a block switch, not a turned count.
- To get nearer one traitor, change the INPUTS (stage byte and money rows), reasoning with sum >= 7: stage 2-3 bots holding >= 750k against a poor row 0 already qualify. First rule out item 6: no used crew slot or row 0 may read as -1 in the shadow.
- Optional Arcade-like limiter without a cap: limit how many Evaluate calls per bot reach the 30% roll (it runs on every call all round).
- Fix wording in the diag/comments: the limit test is `>=` (confirmed at 0x79b956); the comment at klbrain_logic.h:306 only marks the money-threshold compares as GUESS (those are `jae` too, confirmed at 0x79b8e9..0x79b923).
