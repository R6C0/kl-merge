# The Vault, W8: a fault inside d3d9.dll on the render thread (2026-10-12, offline reading of KLHook_1.dmp)

Dump and log: `<work>/research/crash_1012_vault_d3d9/` (KLHook_1.dmp 49.6 MB, W8_vault_gates_pb.log). Compared with W7 (`<work>/build/klhook/live/W7_vault_gates.log`).
Labels: MEASURED (dump / log), READ (code), ASSUMED, GUESS. Scratch scripts: `C:/kl_scratch/vault_w8/crash/` (rd.py, disx.py).
The dump is NOT a full-memory dump (stacks + a few heap pages): the d3d9 device's fields at +0x2bd8 and the stage table at +0x2be8 are not in it.

## 1. What faulted (MEASURED)
- c0000005 at d3d9.dll+0x5feeb, reading 0x6. Thread 48956 = the render thread (frame chain 0x56139e = loop 0x561330 -> 0x7c286d -> 0x886e1f -> 0x5c560d). The main thread (50172) stands at 0x841bb1 < 0x459b20 = WaitForSingleObject on the render thread, no timeout (the game's normal hand-off).
- The local `C:/Windows/SysWOW64/d3d9.dll` is the one in the process: the 0x100 bytes of d3d9 code the dump holds (0x6becfe6b..) equal the disk copy, so the offsets below are exact.
- The 6 is not an argument. It is `eax + 4` with eax = 2: d3d9 internal function 0x5fea0 (called from the DrawPrimitive entry, d3d9+0x84668, stack `ret 0x6bef4668`) does
  `ebx = stage_table[idx]` (idx = 0, `[device+0x20] + 0x2be8 + 4*idx`, idx < 8: the TEXTURE STAGES), `eax = [ebx+8]` (a vtable), `edi = [eax+0xc]` (slot 3), `call edi` with ecx = ebx+8, then `mov ecx,[eax+4]; cmp ecx,3` (3 = D3DRTYPE_TEXTURE). It expects slot 3 to return a pointer to the resource description (format at +0, type at +4). The call returned 2.

## 2. The d3d9 call the game made (READ + MEASURED)
- kl2 0x5c55f0 is the wrapper `device->vtbl[0x144/4 = 81]` = IDirect3DDevice9::DrawPrimitive(type 5 = TRIANGLESTRIP, start 0, primitive count 2) (arguments on the stack: 5, 0, 2, device 1a526460).
- Its caller kl2 0x886c10 draws one screen-space quad: it fills a dynamic vertex buffer (the object [0xf645c0]; 4 vertices of 0x1c bytes, the corner values 255.0 / 256.0 are on the stack), SetStreamSource(0, [obj+0x18], 0, 0x1c), SetFVF(0x144), DrawPrimitive, SetStreamSource(0, null). The vertex buffer is not the culprit: the failing check is on texture STAGE 0.
- kl2 0x7c1c30 is the render thread's COMMAND INTERPRETER (a switch of 0x7a opcodes, jump table 0x7c4c24 / byte table 0x7c4d4c, records [op][..][size at +0x18]). The command being run is in the dump at 1a210870: opcode 0x64 = a separable GAUSSIAN BLUR pass (handler 0x7c25a5..0x7c289b: 4 taps, weights exp(-i^2/(2 sigma^2)), the texture's GetLevelDesc, SetRenderState 0x1b = 0, SetTexture(0, [cmd+0x20]) through the game's wrapper 0x76bd60, which calls IDirect3DDevice9::SetTexture (vtbl 0x104) with the pointer unchanged, then the quad). Fields: [+0x1c] = 0 (first pass of the pair), [+0x20] = 23998680 (source texture interface), [+0x24] = 1.6 (0x3fcccccd, sigma), [+0x28] = 2397fc80 (destination surface). The next records are 0x26 (set render target) and a second 0x64 with [+0x1c] = 1 (the vertical pass), source 23999460, destination 23981a40.
- The producer is kl2 0x6627a0 (it builds 0x26 / 2 / 0x64 / 0x26 / 2 / 0x64 ... records, buffers [edi+0x1800..0x1818] of the object at [renderer+0x48], sizes = the backbuffer / 2: a half-resolution glow / bloom style post chain). WHAT EFFECT IT IS (bloom, heat haze, damage blur, fire glow) is NOT established.

## 3. The object in stage 0 (MEASURED)
- ebx = 23998620, a d3d9 internal object of the class constructed by d3d9 0x4bc00: vtbl[0] 6be72310 (+0x2310), [+8] = 6be7236c (+0x236c), [+0x14] = the device, [+0x60] = 6be7229c (the public texture interface, = 23998680 = the game's cmd+0x20, so the game's source texture IS this object), +0x68 = 0x72 (D3DFMT_R32F), +0x6c = 3 (D3DRTYPE_TEXTURE), +0x70 = 0x08000001 (D3DUSAGE_RENDERTARGET | internal), +0x80 / +0x84 = 256 x 256, +0x30 / +0x34 = (1, 0).
- Two more objects of this class are in the dump: 23998880 (also R32F 256x256, usage 0x08000001, [+8] = 0x236c) and 23998760 (A8R8G8B8 64x64, usage 0x0c000000, [+8] = **0x22f4**). READ: the two sub-object vtables differ in slot 3. In the 0x22f4 table slot 3 = `lea eax,[ecx+0x60]; ret` (returns the description, what 0x5fea0 expects). In the 0x236c table slot 3 = d3d9+0x70140 = a fence check: `if (device fence (2bdc:2bd8) is past this resource's fence (+0x2c:+0x28)) ret; else jmp 0x4fcad (flush)`; both exits return a NUMBER or an HRESULT, never a pointer. Here the device's low fence word was past the resource's (2 > 1, high words 0 = 0 assumed), the early `ret` left eax = 2. So with this object in stage 0 the fault is certain: it does not depend on a timing; what is open is why a 0x236c-flavoured R32F render target is in the stage table when the check runs.
- WHAT THIS MEANS, and what it does not: the two vtables look like two states or two flavours of one class (0x22f4 = sampleable texture, 0x236c = the render-target base state). ASSUMED (not shown): 0x236c is the state of a texture that is still the CURRENT RENDER TARGET, i.e. the blur pass sampled a texture it was still rendering into (a read-while-write hazard: the preceding 0x26 record, which sets the target, did not switch away from it, or a render-target surface reset left the texture in that state). The alternative, that d3d9 swaps the vtable for another reason (a device reset / a lost-device recovery; the earlier stall below), is equally unrefuted. The 0x70140 reading also leaves one thing unexplained: a normal run binds R32F render-target textures every frame (W7: 197 s, 428,124 frames, no fault), so either the normal ones carry 0x22f4, or the early `ret` is never taken; nothing in the dump decides it (device fence fields are not captured).

## 4. The 500 ms and the main thread (MEASURED)
- 08:39:42.794 is the last tick-driven `bots: L1` line (they come every 1.09 s). At 44.084 `talk / escort: the tick is not on the game's thread` = the hook's fallback saw no SteamAPI_RunCallbacks call for 500 ms, and the bots line at 44.084 / 45.091 / 46.577 came from the fallback thread. The crash is at 45.547. So the main loop made no step for at least 1.3 s and at most 2.7 s before the fault, and the dump shows why: it waits (no timeout) for the render thread. THE RENDER THREAD WAS THEREFORE BUSY OR BLOCKED FOR 1.5 - 2.7 s BEFORE IT REACHED THIS DRAW. Where it stood is not in the dump (it ran straight on into the fault; its old stack below esp holds only the dump writer's frames).
- READ: the flush path 0x4fcad of the same fence function waits for the GPU (it calls the resource manager at [device+0x2be0], vtbl +0x34). A previous draw's wait on a slow GPU / driver (NVIDIA nvwgf2um on the stack, the 640x480 monitor-off mode, overlays: gameoverlayrenderer, nvspcap, medal-hook32 are loaded) is consistent with the stall and with the fence counters having moved, but is not proven.
- The nudge counter of W8 follows W7's: 12-14k calls/s while loading and before GO, then the frame-paced ~450-520/s (W8 4,649/s in the 10 s window that holds GO, 445/s in the next; W7 518-530/s throughout). No frame-rate collapse before the stall.
- The rest of the process: no other thread is in d3d9 inside a call (thread 41068 is d3d9's own window/focus thread 0x746e0 in win32u; the 1.6 MB-stack pool threads wait at kl2 0x92699f / 0x9a8fb6). No KLHook (dinput8.dll) frame lies on the live render stack: the chain is kl2 + d3d9 only.
